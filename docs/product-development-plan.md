# Furniture OS — план продуктовой разработки после миграции

Дата: 25 августа 2026 года.

Статус: план нового функционала. Он запускается только после выполнения критериев завершения [`technology-migration-plan.md`](technology-migration-plan.md) и отдельной приёмки технической миграции.

Архитектурные решения, DDD-правила, границы MVP и тестовые требования определены в [`project-plan.md`](project-plan.md).

## 1. Условие старта

Продуктовая разработка не начинается, пока:

- текущий React-интерфейс не перенесён в `apps/web`;
- Symfony API не работает в `apps/api`;
- существующий прототипный расчёт не переключён с TypeScript на API с подтверждённым parity;
- PostgreSQL, Docker, OpenAPI, CI/CD и локальный storage adapter не настроены;
- старые migration flags и runtime fallback не удалены;
- migration completion ADR не принят владельцем проекта.

Если во время продуктовой работы обнаружен дефект миграции, он исправляется отдельным техническим PR с regression-тестом и не смешивается с новой функцией.

## 2. Принцип реализации функций

Каждая функция реализуется вертикальным срезом:

```text
Domain rule
→ Application use case
→ Infrastructure adapter/persistence
→ OpenAPI
→ generated frontend client
→ UI
→ unit/application/integration/API/E2E tests
```

Один PR должен давать проверяемое приращение пользовательского сценария. Не создаются заранее пустые модули, таблицы или универсальные платформы без ближайшего use case.

## 3. Этап 0 — подтвердить продуктовые решения

До реализации зафиксировать решения владельца:

1. первый пилотный город;
2. прямой распашной шкаф как единственная категория MVP-1;
3. конструктив, диапазоны размеров и допустимое наполнение;
4. обязательные поля технического задания;
5. правила предварительной цены и округления;
6. модель пользователей, организаций и ролей;
7. управляемая RFQ-площадка вместо открытого аукциона;
8. отсутствие платежей и escrow в первых двух MVP.

Параллельно провести интервью минимум с 10 покупателями и 10 производителями и получить готовность 5–10 производителей участвовать в городском пилоте.

Критерий выхода: решения оформлены ADR/доменным словарём, минимум пять производителей готовы рассчитывать стандартизированные заявки.

## 4. Этап 1 — утверждённый доменный контракт ruleset-v1

### Шаг 1.1. Уточнить ubiquitous language

- Определить термины CabinetDraft, CabinetRevision, Section, Filling, Material, Hardware, ValidationResult, CalculationSnapshot и PriceEstimate.
- Зафиксировать владельцев данных и границы контекстов Cabinet, Catalog, Calculation и Pricing.
- Разделить ошибки, блокирующие revision/RFQ, и предупреждения, требующие внимания.

### Шаг 1.2. Зафиксировать схемы

- `CabinetDraftV1` — пользовательский изменяемый ввод.
- `CabinetRevisionV1` — неизменяемая нормализованная версия.
- `ValidationResultV1` — код, severity, field path и параметры.
- `CalculationSnapshotV1` — BOM/оценка с версиями правил, каталога и прайса.
- Размеры — целые миллиметры; деньги — целые копейки плюс валюта.

### Шаг 1.3. Создать golden fixtures

- 10–15 подтверждённых технологом валидных шкафов.
- Невалидные и граничные случаи ширины, высоты, глубины, секций, полок, штанг и ящиков.
- Ожидаемые ошибки, предупреждения, нормализованная геометрия, BOM и стоимость.
- Отдельные `rulesetVersion`, `catalogVersion`, `priceListVersion`.

Проверки: все fixtures выполняются на backend; property tests граничных величин; mutation testing критических правил.

Критерий выхода: `ruleset-v1` утверждён технологом и владельцем; prototype-v0 больше не определяет продуктовые правила.

## 5. Этап 2 — Identity и безопасность

### Шаг 2.1. Реализовать Identity

- User, Organization, Membership и Role как отдельный bounded context.
- Same-origin session cookie: HttpOnly, Secure, SameSite.
- Регистрация может быть закрытой/invite-only для пилота.
- Recovery и смена пароля без хранения открытых токенов.

### Шаг 2.2. Ввести авторизацию

- Object-level access для Project, Revision, File, Document, RFQ и Offer.
- Application use cases проверяют actor/organization, controller не заменяет бизнесовую авторизацию.
- CSRF, rate limits, security headers, аудит входов и критических действий.

Проверки: authentication matrix; IDOR; CSRF; rate-limit; две организации не видят данные друг друга.

Критерий выхода: пользователь безопасно входит, а изоляция организаций доказана API/security-тестами.

## 6. Этап 3 — проекты, черновики и неизменяемые ревизии

### Шаг 3.1. Project

- Создание, переименование, список, архивирование и открытие проекта.
- Project принадлежит организации/пользователю.
- Сначала минимальный список без сложного поиска и тегов.

### Шаг 3.2. CabinetDraft

- Сохранение текущей конфигурации как изменяемого draft.
- Optimistic concurrency/version для защиты от потери параллельных изменений.
- Autosave с debounce; понятные состояния saving/saved/conflict/error.

### Шаг 3.3. CabinetRevision

- Создание revision только из допустимого нормализованного draft.
- Revision неизменяема и имеет sequence, schema version, автора и timestamp.
- Старые revision никогда не изменяются при обновлении draft или ruleset.

Проверки: domain invariants; repository integration; conflict cases; API access; E2E create → edit → save → reopen → create revision.

Критерий выхода: пользователь создаёт проект, сохраняет черновик, выпускает ревизию и может открыть историю без изменения старых данных.

## 7. Этап 4 — рабочий пошаговый конфигуратор

Порядок экранов MVP:

1. размеры;
2. число и ширина секций;
3. наполнение: полки, штанга, типовой блок ящиков;
4. материалы корпуса и фасада;
5. итог, ошибки и предупреждения.

Технические правила:

- Zustand хранит только draft и историю undo/redo;
- TanStack Query хранит серверные данные;
- быстрый локальный preview не утверждает производственную корректность;
- backend возвращает авторитетную нормализацию и validation result;
- недоступность backend не подменяется локальной «окончательной» ценой.

Проверки: component tests каждого шага; accessibility; autosave/conflict; responsive visual regression; E2E полного пути.

Критерий выхода: пользователь самостоятельно создаёт допустимую ревизию одного распашного шкафа.

## 8. Этап 5 — CalculationSnapshot и предварительная цена

### Шаг 5.1. Calculation

- Отделить геометрию, детали, фурнитуру и предупреждения от Pricing.
- Выполнять расчёт только по immutable revision.
- Версионировать ruleset и каталог.

### Шаг 5.2. Pricing

- Материалы, фурнитура, работа, доставка и margin считаются отдельными компонентами.
- Цена хранится в копейках; float для денег запрещён.
- Snapshot фиксирует `priceListVersion`; обновление прайса не меняет историю.
- Значение явно маркируется как предварительная оценка Furniture OS.

### Шаг 5.3. SVG

- Параметрический технический вид строится из нормализованной конфигурации.
- Открытый/закрытый вид, секции, наполнение и основные размеры.
- SVG не содержит собственных бизнес-формул.

Проверки: golden fixtures 100%; boundary/property; SVG snapshots; historical price immutability; E2E revision → estimate.

Критерий выхода: revision получает воспроизводимый versioned snapshot и точный технический SVG.

## 9. Этап 6 — документы и локальные файлы

### Шаг 6.1. Подключить Messenger

- Doctrine transport в PostgreSQL на первой очереди.
- Message ID, idempotency key, retry strategy и dead-letter transport.
- Handler вызывает application use case и не содержит доменных правил.

### Шаг 6.2. Генерировать ТЗ

- JSON и HTML/PDF строятся по конкретным revision и calculation snapshot.
- Сохраняются через существующий FileStorage port.
- Фиксируются template version и input checksum.
- Повторный job не создаёт дубликаты.

### Шаг 6.3. Защитить файлы

- MIME/size limits, авторизованная выдача, audit trail удаления.
- Локальный каталог вне web-root и включён в backup/restore.

Проверки: handler idempotency; storage contracts; authorization; PDF smoke; E2E создать и скачать ТЗ.

Критерий выхода: пользователь получает воспроизводимое ТЗ по неизменяемой ревизии.

## 10. Этап 7 — подготовить управляемый RFQ-пилот

### Шаг 7.1. Supplier

- Ручной onboarding производителя.
- Регион, категории, материалы, возможности, минимальный заказ и статус проверки.
- Кабинет можно заменить защищённой упрощённой формой для первого пилота.

### Шаг 7.2. RFQ

- RFQ привязан ровно к одной immutable revision и calculation snapshot.
- Подбор 3–5 производителей по региону и capability profile.
- Deadline, статусы приглашений и audit events.

### Шаг 7.3. SupplierOffer

- Отдельные поля мебели, материалов, замен, замера, доставки, подъёма, монтажа, срока, гарантии, НДС и срока действия.
- Предварительная цена отделена от подтверждённой после замера.
- Offer после отправки версионируется либо становится неизменяемой.

### Шаг 7.4. Сравнение

- Сопоставимые строки цены и условий.
- Никакого автоматического выбора самого дешёвого предложения.
- Видны полнота, срок, гарантия и допустимые замены.

Проверки: Workflow transitions; authorization supplier/customer; deadline; idempotent invitations; immutable links; E2E send RFQ → two offers → compare.

Критерий выхода: реальный пользователь получает минимум два сопоставимых предложения по одной ревизии.

## 11. Этап 8 — замер и подтверждённое предложение

- Выбор производителя без платежа внутри платформы.
- Статусы согласования замера.
- ConfirmedOrderSpecification после профессионального замера.
- Окончательная цена и причины отклонения от предварительной.
- Журнал переходов, ответственных и времени.

Проверки: допустимые/недопустимые Workflow transitions; audit; price deviation; права сторон.

Критерий выхода: пилот измеряет конверсию предложение → замер → договор и отклонение итоговой цены.

## 12. Этап 9 — hardening пилота

- Backup/restore drill БД и файлов.
- Accessibility основного пути.
- Нагрузочные проверки расчёта, документов и RFQ fan-out.
- Structured logs, error tracking и продуктовые метрики.
- Privacy review, retention и удаление данных.
- Верификация производителей и операционные SLA.

Критерий выхода: пилот можно эксплуатировать и восстанавливать с согласованными RPO/RTO.

## 13. Этап 10 — AI-эксперимент, только после MVP-2

- Контрольный PNG из технического SVG.
- Provider adapter и Messenger job.
- Provider/model/promptVersion/input checksum/cost/retry/status.
- Кеш одинаковых запросов, лимит расходов и opt-out.
- Результат явно маркируется концептуальным и не влияет на BOM/цену.

Критерий выхода: решение KILL/ITERATE/SCALE принимается по влиянию на завершение конфигуратора и отправку RFQ.

## 14. Отложенные возможности

До подтверждения продуктовой необходимости не начинаются:

- полноценный 3D и Three.js;
- кухни и сложная встроенная мебель;
- производственный nesting;
- CNC/CAD/CAM;
- автоматический onboarding производителей;
- платежи, escrow и арбитраж;
- микросервисы, Go, Redis, RabbitMQ и Kubernetes.

Каждая такая возможность требует отдельного ADR, метрики необходимости и обновления основного плана.

## 15. Будущая замена local storage российским S3

Выполняется только при эксплуатационной необходимости:

1. выбрать российского провайдера вместе с основной инфраструктурой;
2. реализовать S3 adapter без изменения application-порта;
3. запустить существующий storage contract suite;
4. переключить новые записи на S3;
5. включить dual-read с local fallback;
6. идемпотентно копировать старые объекты пакетами;
7. сверять size/checksum и фиксировать backend объекта;
8. после наблюдения отключить fallback;
9. удалять local copies только отдельным согласованным изменением.

Критерий выхода: use cases и API не изменились, consistency scan и contract tests проходят.

## 16. Последовательность продуктовых релизов

1. `Domain v1`: словарь, contracts и golden fixtures.
2. `Identity`: пользователи, организации и изоляция данных.
3. `Projects`: проекты, autosave draft и immutable revisions.
4. `Configurator`: пошаговый пользовательский сценарий.
5. `Estimate`: calculation/pricing snapshot и SVG.
6. `Specification`: Messenger, JSON/PDF и локальные файлы.
7. `RFQ pilot`: suppliers, invitations, offers и сравнение.
8. `Measurement`: подтверждённая спецификация и цена.
9. `Pilot hardening`: эксплуатация, безопасность и метрики.
10. `AI experiment`: только после проверки marketplace MVP.

Переход к следующему релизу разрешён только после выполнения критерия выхода предыдущего.

## 17. Тестовые требования для каждой функции

- Domain unit tests всех инвариантов и переходов.
- Application tests успешного пути, ошибок, авторизации и идемпотентности.
- PostgreSQL integration tests repository/migrations.
- API schema, error и access-control tests.
- Component tests новых UI-состояний.
- E2E основного пользовательского результата функции.
- 100% golden fixtures; не ниже 90% строк/ветвей критических модулей; общее покрытие не ниже 80%.
- Исправление дефекта начинается с regression-теста.

## 18. Определение готовности MVP-1

- пользователь входит и создаёт проект;
- настраивает один распашной шкаф;
- получает серверные ошибки/предупреждения и предварительную цену;
- создаёт immutable revision;
- видит технический SVG;
- получает JSON/PDF ТЗ;
- история воспроизводится по версиям правил, каталога и прайса;
- основной путь покрыт E2E и проходит accessibility-проверку.

## 19. Определение готовности MVP-2

- оператор ведёт 5–10 проверенных производителей одного города;
- RFQ отправляется 3–5 подходящим производителям;
- предложения нормализованы и привязаны к одной revision;
- пользователь сравнивает минимум два предложения;
- предварительная и подтверждённая цены разделены;
- статусы и действия журналируются;
- собираются продуктовые метрики пилота;
- платежи и escrow не требуются.
