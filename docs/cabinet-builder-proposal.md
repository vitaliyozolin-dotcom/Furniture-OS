# Вход, конструктор и публикация шкафа — предложение реализации

Дата: 15 октября 2026 года. Статус: владелец разрешил реализацию. Принятые границы и трактовка публикации зафиксированы в [ADR-0006](adr/0006-cabinet-builder-pilot.md); миграция не объявляется принятой.

## Запрошенный результат

На первой странице доступны вход и регистрация. «Новый шкаф» открывает конструктор, где пользователь задаёт конфигурацию и видит её изображение. После сохранения можно опубликовать выбранный шкаф.

Референс: [конструктор «Привет Макет»](https://privetmaket.ru/shkaf/), просмотрен 15 октября 2026 года. Для первого среза предлагаются его основные способы настройки: габариты, секции, наполнение и материалы рядом с изображением изделия. Референс содержит больше мебельных категорий и производственных настроек, чем утверждённая категория Furniture OS; их перенос не подразумевается.

## Предлагаемый пользовательский путь

1. На главной странице — действия «Войти» и «Регистрация», после входа — имя и выход.
2. «Новый шкаф» открывает отдельный экран конструктора. Настройку можно начать до входа; вход нужен перед сохранением в аккаунт и публикацией, при этом введённая конфигурация сохраняется.
3. Конструктор одного прямого распашного шкафа: ширина, высота, глубина; добавление/удаление секций в границах MVP; полки, штанга и ящики; доступные материалы корпуса и фасадов. Рядом — параметрический SVG с открытым/закрытым видом и размерами. Предусмотреть undo/redo, ошибки полей и состояния загрузки/недоступности расчёта.
4. Пользователь задаёт название проекта и сохраняет черновик на backend. В разделе «Проекты» видит только свои проекты, может открыть и продолжить настройку. Параллельное сохранение проверяет версию черновика.
5. Публикация фиксирует неизменяемую ревизию. Последующие изменения черновика не меняют ранее опубликованную конфигурацию. Перед публикацией видны состав раскрываемых данных и кнопка явного подтверждения.

## Решение по публикации

**Принято:** публичная карточка заявки по ссылке, которую автор передаёт изготовителям самостоятельно. Ниже сохранены варианты исходного предложения; окончательные границы — в ADR-0006.

Нужно выбрать один из двух сценариев либо явно разрешить оба:

- **Заявка производителям (RFQ)** — «хочу заказать такой шкаф»: ревизия, город, описание пожеланий и срок ответа. Это направление соответствует RFQ-first плану. Подбор производителей и доставка приглашений требуют отдельного согласованного onboarding; отсутствие реальных получателей нельзя показывать как успешную отправку.
- **Публичная карточка по ссылке** — «показать мой шкаф»: опубликованная ревизия, SVG, название и публичное описание. Email, приватные заметки и данные аккаунта не раскрываются. Автор может снять карточку с публикации. Публичная галерея/каталог является новым продуктовым решением и требует фиксации в плане.

До ответа владельца нельзя выбирать, какие данные становятся публичными, или выдавать сохранённый черновик за отправленную производителям заявку.

## Контексты и границы

- **Identity:** регистрация, вход, выход и текущий пользователь; Symfony Security и серверная сессия с HttpOnly/SameSite, Secure при HTTPS, хеш пароля, CSRF и ограничение попыток входа. Минимальная модель индивидуального аккаунта; организация/членство определяются отдельно, если они нужны для первого сценария.
- **Project:** владелец, черновик, версия, immutable revision и список собственных проектов. Application use cases проверяют владельца при каждом обращении; доступ по чужому ID отклоняется.
- **Cabinet/Calculation:** конфигурация, её проверка, нормализованное описание для SVG и предварительный расчёт. Публичные межконтекстные application-контракты вместо доступа к внутренним ORM-классам.
- **Marketplace/публичная публикация:** появляется только после уточнения смысла публикации; хранит ссылку на конкретную immutable revision, а не изменяемый draft.

Стек остаётся React/TypeScript/Vite + PHP 8.4/Symfony 7.4 + PostgreSQL/Doctrine. OpenAPI изменяется до реализации endpoint-ов, затем генерируются frontend-типы. Frontend не считает авторитетную цену и BOM.

## Точность и продуктовые ограничения

Производственные правила `ruleset-v1` пока не приняты технологом. Реализация форм не является подтверждением производственной пригодности шкафа. Перед разработкой нужно в исключении явно определить: выполняется демонстрационный конструктор с существующим предварительным `prototype-v0` расчётом либо сначала принимаются продуктовые fixtures/правила. Не следует молча выдавать произвольные ограничения интерфейса за утверждённый конструктив.

Полноценные 3D, кухни, купе, CNC и платежи не входят в предложенный первый срез. AI-интеграция уже существует отдельно; новый пользовательский сценарий не должен зависеть от наличия платного AI-ключа.

## Проверка готовности

- Domain/application: конфигурация, неизменяемость ревизии, владение, сохранение и конфликт версий, переход публикации/снятия.
- PostgreSQL: миграции с пустой и предыдущей схемы, уникальность email, сохранность проектов.
- API/security: регистрация/вход/выход, сессия и CSRF, чужие проекты, приватные поля публичного ответа, ограничения запросов.
- UI: формы, сообщения ошибок, сохранение введённого при входе, SVG по конфигурации, undo/redo, мобильная компоновка.
- E2E: главная → регистрация → новый шкаф → настройка → сохранение → повторное открытие → публикация выбранного типа; отдельный второй аккаунт не получает доступ к приватному проекту.
- Существующие coverage gates, typecheck, архитектурные проверки и `git diff --check` обязательны.

[План миграции, §0](technology-migration-plan.md#0-граница-плана) до приёмки запрещает регистрацию, проекты и новый конфигуратор. По [ADR-0004](adr/0004-migration-acceptance.md) миграция пока не принята; ранее согласованное исключение [ADR-0005](adr/0005-local-ai-integration.md) относится только к локальному AI.

Для реализации этого запроса требуется отдельное разрешение на Identity + Projects + демонстрационный конструктор + выбранный сценарий публикации до приёмки миграции. После ответа сначала обновляются утверждённый план и ADR, затем выполняется реализация отдельными проверяемыми срезами. Текущие незакоммиченные изменения Docker сохраняются отдельно от этих продуктовых изменений.
