# Furniture OS — инструкции для агентов

Эти инструкции действуют для всего репозитория.

## Обязательный контекст

Перед анализом архитектуры, составлением плана или изменением кода полностью прочитайте:

1. [`docs/project-plan.md`](docs/project-plan.md) — утверждённые продуктовые и архитектурные решения;
2. [`docs/technology-migration-plan.md`](docs/technology-migration-plan.md) — перенос текущего прототипа на целевой стек без нового функционала;
3. [`docs/product-development-plan.md`](docs/product-development-plan.md) — новый функционал, разрешённый только после отдельной приёмки миграции.

Это исполнимые планы проекта, а не справочные документы.

Не смешивайте миграцию и продуктовую разработку. Пока критерии завершения технической миграции не выполнены и не приняты владельцем, выполняйте только `technology-migration-plan.md`. После приёмки новые функции выполняются по `product-development-plan.md` отдельными вертикальными срезами.

Все решения и изменения должны соответствовать ему. Особенно обязательны:

- React + TypeScript + Vite для frontend;
- PHP 8.4 + Symfony 7.4 LTS для единственного backend MVP;
- PostgreSQL и Doctrine;
- модульный монолит без преждевременных микросервисов;
- DDD с направлением зависимостей `Presentation → Application → Domain` и реализацией портов в `Infrastructure`;
- отсутствие зависимостей Domain от Symfony, Doctrine, HTTP, файловой системы и внешних SDK;
- локальное файловое хранилище MVP только через application-порт и сменяемый infrastructure-адаптер;
- возможность последующей миграции на российское S3-совместимое хранилище без изменения Domain и use cases;
- авторитетные расчёты, BOM и цены только на backend;
- RFQ-first границы MVP; AI и 3D не должны блокировать основной сценарий;
- тесты как обязательная часть каждого изменения и соблюдение порогов/типов проверок из раздела «Тестирование» плана.

## Перед изменением

1. Определите затрагиваемый bounded context и слой.
2. Проверьте соответствующий этап roadmap и архитектурные запреты в плане.
3. Сначала зафиксируйте ожидаемое поведение тестом, если меняется бизнес-правило или исправляется дефект.
4. Не расширяйте технологический стек и границы MVP без явного решения владельца проекта.

## При реализации

- Держите бизнес-правила в Domain, orchestration — в Application, интеграции — в Infrastructure, транспорт — в Presentation.
- Обращайтесь к другому модулю через явный контракт, а не через его таблицы, Doctrine entities или внутренние классы.
- Не передавайте абсолютные пути, публичные URL и тип конкретного storage-провайдера в Domain или Application.
- Добавляйте unit-тесты доменных правил, application-тесты use cases и необходимые integration/contract/API/E2E-тесты пропорционально изменению.
- Сохраняйте обратную совместимость OpenAPI либо явно документируйте несовместимое изменение.

## Изменение утверждённого плана

Если запрос противоречит `docs/project-plan.md`, не меняйте архитектуру молча. Укажите противоречие и получите явное решение владельца. После решения сначала обновите план и только затем реализацию.

Новые значимые архитектурные решения фиксируйте в плане или отдельном ADR со ссылкой из плана. Не дублируйте расходящиеся версии правил в нескольких документах.

## Проверка готовности

Перед завершением работы запустите релевантные тесты, typecheck, архитектурные проверки и `git diff --check`. Сообщите, что было проверено, а что запустить не удалось.
